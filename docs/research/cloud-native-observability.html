核心发现

三大支柱正在融合，OpenTelemetry 成为通用语言

传统指标、日志、追踪三信号各自独立的格局正在瓦解。OpenTelemetry 以统一 SDK 和语义约定，成为跨项目数据交换的事实标准，显著降低了多信号关联的集成成本。

Grafana LGTM 堆栈形成三信号闭环标准

Loki（日志）+ Grafana（可视化）+ Tempo（追踪）+ Mimir（指标）构成完整闭环，提供从数据采集到仪表盘的一站式体验，成为新兴项目事实上的对标基准。

ELK 在全文搜索场景不可替代

Elasticsearch 的倒排索引和全文搜索能力在日志分析领域仍无对手。Loki 虽在成本上有优势，但面对复杂搜索场景时能力差距明显，两者将在不同场景下长期共存。

PromQL 的标签模型影响 LogQL 和 TraceQL

Prometheus 基于标签（label）的查询模型被 Loki 的 LogQL 和 Tempo 的 TraceQL 继承，形成 PromQL 思想的查询语法家族，大幅降低了用户在多系统间的学习成本。

核心趋势

OpenTelemetry 生态爆发

OpenTelemetry 贡献者已超过 1,800 人，成为仅次于 Kubernetes 的 CNCF 第二大贡献者社区。其统一的 Instrumentation 框架正逐步取代 OpenTracing 与 OpenCensus，成为可观测性数据采集的事实标准。

三大信号融合

指标、日志与追踪的界限日益模糊。OpenTelemetry 通过 TraceID 将三者关联，Grafana 的 Explore 支持跨信号联合查询，ELK 也在引入 APM 追踪能力。单一信号分析正让位于多信号关联分析。

eBPF 无侵入式采集

eBPF 技术让内核级别的无侵入数据采集成为可能，无需修改应用代码即可获取网络、文件系统和性能数据。Pixie、Cilium 等项目的崛起标志着可观测性向 Zero-Instrumentation 方向演进。

对象存储成为后端基石

Thanos、Mimir、Loki、Tempo 等新一代可观测性后端均以对象存储（S3 / GCS / MinIO）为底层存储，替代传统的本地盘模式。对象存储的低成本与高扩展性使长期数据留存成为可行，推动 Observability as Data Lake 范式。

ELK Stack 深度分析 第 2 节 / 共 8 节

ELK Stack — 由 Elasticsearch、Logstash、Kibana 三件套构成 — 是云原生可观测性领域最成熟的日志管理与全文搜索解决方案。 随着 Beats 轻量采集器家族的加入，现已演化为完整的 Elastic Stack 生态。 本节从架构、语法、配置、采集四个维度深入拆解 ELK 的核心能力。

ELK 数据流链路： Beats Logstash Elasticsearch Kibana
数据源 → Beats（轻量采集）→ Logstash（解析/转换/增强）→ Elasticsearch（存储/索引/搜索）→ Kibana（可视化/分析/管理）

2.1 Elasticsearch — 分布式搜索与分析引擎

Elasticsearch（以下简称 ES）是基于 Lucene 构建的分布式搜索和分析引擎， 在全文搜索领域是事实上的标杆产品。其水平扩展能力、倒排索引机制、 近实时搜索特性使其在日志分析、应用搜索、安全分析等场景占据主导地位。

2.1.1 集群架构层次

层次 说明 关键属性
Cluster 一个或多个节点的集合，承载全部数据与查询 集群名称标识；跨机房容灾
Node 单个 ES 实例，参与集群 角色：Master / Data / Ingest / Coordinating 等
Index 同类型文档的集合，类似关系数据库中的"表" 分片数与副本数在创建时指定
Shard 索引的物理分片，每个分片是一个完整的 Lucene 索引 Primary Shard + Replica Shard
Segment 分片内部的最小存储单元，不可变 段合并策略影响写入性能

设计要点： ES 通过 分片（Shard） 实现水平扩展，每个索引可拆分为多个主分片分布在集群节点上。 副本分片提供高可用与查询吞吐。段（Segment）的不可变设计使 ES 适合大量写入、 少量更新的日志场景。倒排索引（Inverted Index）是实现毫秒级全文搜索的核心数据结构。

2.1.2 ES Query DSL — 完整语法示例

ES 使用基于 JSON 的查询领域特定语言（DSL）进行搜索与分析。 以下覆盖日常开发中最核心的六类查询与四种聚合类型。

Query match — 全文搜索

对 text 类型字段执行分词匹配，返回按相关性评分排序的结果。

GET /logs-nginx/_search
{
  "query": {
    "match": {
      "message": {
        "query": "connection timeout",
        "operator": "and"
      }
    }
  }
}
Query term/terms — 精确匹配

对 keyword 或数值字段做精确查找，不经过分词器。

GET /logs-nginx/_search
{
  "query": {
    "terms": {
      "http_status": [500, 502, 503]
    }
  }
}
Query range — 范围过滤

适用于时间、数值、IP 范围的区间查询。

GET /logs-nginx/_search
{
  "query": {
    "range": {
      "@timestamp": {
        "gte": "now-1h",
        "lte": "now"
      }
    }
  }
}
Query bool — 组合查询

使用 must / should / filter / must_not 构建复杂逻辑。

GET /logs-nginx/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "message": "error" } }
      ],
      "filter": [
        { "range": { "@timestamp": { "gte": "now-1d" } } },
        { "terms": { "http_status": [500, 502] } }
      ],
      "must_not": [
        { "term": { "host": "monitoring" } }
      ],
      "should": [
        { "match": { "message": "critical" } }
      ],
      "minimum_should_match": 1
    }
  }
}
Query exists — 字段存在性

筛选包含（或不包含）某字段的文档，适用于检测缺失字段。

GET /logs-nginx/_search
{
  "query": {
    "exists": {
      "field": "stack_trace"
    }
  }
}
Query 通配符与正则

适用于模糊匹配场景，注意性能消耗较大。

GET /logs-nginx/_search
{
  "query": {
    "wildcard": {
      "url.keyword": "/api/v2/order*"
    }
  }
}

2.1.3 聚合分析（Aggregations）

聚合是 ES 的分析核心，分为 Bucket（分桶）、Metric（指标）、 Pipeline（管道）三种类型。以下展示五种最常用聚合的组合使用。

Bucket terms 聚合

按字段值分组计数，类似 SQL 的 GROUP BY。

GET /logs-nginx/_search
{
  "size": 0,
  "aggs": {
    "top_status": {
      "terms": {
        "field": "http_status",
        "size": 10,
        "order": { "_count": "desc" }
      }
    }
  }
}
Bucket date_histogram

按时间区间分桶，时间序列分析的基石。

GET /logs-nginx/_search
{
  "size": 0,
  "aggs": {
    "requests_over_time": {
      "date_histogram": {
        "field": "@timestamp",
        "fixed_interval": "5m",
        "min_doc_count": 0
      }
    }
  }
}
Metric avg / sum

数值指标计算，支持 avg、sum、min、max、stats。

GET /logs-nginx/_search
{
  "size": 0,
  "aggs": {
    "response_stats": {
      "stats": {
        "field": "response_time_ms"
      }
    }
  }
}
Metric cardinality

去重计数，近似计算，适合大基数场景。

GET /logs-nginx/_search
{
  "size": 0,
  "aggs": {
    "unique_users": {
      "cardinality": {
        "field": "user_id",
        "precision_threshold": 40000
      }
    }
  }
}
复合 terms + date_histogram + avg 嵌套聚合

以下示例展示三层嵌套聚合：先按状态码分组，再按时间区间分桶，计算平均响应时间。

GET /logs-nginx/_search
{
  "size": 0,
  "aggs": {
    "by_status": {
      "terms": { "field": "http_status", "size": 10 },
      "aggs": {
        "over_time": {
          "date_histogram": { "field": "@timestamp", "fixed_interval": "10m" },
          "aggs": {
            "avg_response": {
              "avg": { "field": "response_time_ms" }
            }
          }
        }
      }
    }
  }
}

2.2 Kibana — 可视化与交互分析层

Kibana 是 Elastic Stack 的图形化前端，提供从数据探索到仪表盘展示的完整可视化工作流。 它与 ES 深度集成，无需额外数据管道即可即时查询和展示索引数据。

功能模块 定位 核心能力
Discover 数据探索 实时搜索、过滤、字段浏览；KQL 查询语法支持；时序/Latency 可视化
Dashboard 仪表盘组装 拖拽式面板布局；支持 Markdown、TSVB、Vega 等可视化类型
Dev Tools 开发者工具 内嵌 Console 执行 ES REST API；Painless Lab 调试脚本
Canvas 像素级设计 自由布局的数据展示画布；适用于大屏监控场景
Maps 地理信息 基于 Elastic Maps Service 的地理数据可视化
Alerting 告警管理 基于 ES 查询的规则引擎；支持多种通知渠道
ML 机器学习 异常检测、时序预测、日志分类（需白金版许可）

Kibana 突出优势： （1）与 ES 同进程通信，查询延迟极低；（2）KQL（Kibana Query Language）提供类似 Lucene 的简洁查询语法； （3）支持 TSVB（Time Series Visual Builder）构建复杂时序图，无需编写 DSL； （4）Dashboard 支持仪表盘级联过滤器（Dashboard Filtering），跨图表联动筛选。

Logstash 是 ELK 栈中的数据处理中间件，采用 input → filter → output 的三段式管道架构，负责数据的采集、解析、转换、增强和输出，是连接 Beats 与 ES 的核心枢纽。

2.3.1 完整 Pipeline 配置示例

以下 Logstash 配置从 Beats 接收 Nginx 日志，经 Grok 解析、GeoIP 地理定位后写入 ES：

input {
  beats {
    port => 5044
    ssl => true
    ssl_certificate_authorities => ["/etc/logstash/ca.crt"]
  }
}

filter {
  # 解析 Nginx 标准日志格式
  grok {
    match => {
      "message" => "%{COMBINEDAPACHELOG}"
    }
  }

  # 解析时间戳并覆盖 @timestamp
  date {
    match => ["timestamp", "dd/MMM/yyyy:HH:mm:ss Z"]
    target => "@timestamp"
  }

  # IP 地理定位
  geoip {
    source => "clientip"
    fields => ["city_name", "country_name", "location", "region_name"]
  }

  # 字段类型转换
  mutate {
    convert => { "response" => "integer" }
    convert => { "bytes" => "integer" }
    rename => { "http_host" => "[host][name]" }
  }
}

output {
  elasticsearch {
    hosts => ["https://es-cluster:9200"]
    index => "nginx-logs-%{+YYYY.MM.dd}"
    user => "${ES_USER}"
    password => "${ES_PASS}"
    ecs_compatibility => "main"
  }
}

2.3.2 Grok 模式详解

Grok 是 Logstash 的核心解析工具，利用预定义或自定义的正则模式将非结构化文本映射为结构化字段。 Grok 模式的基础语法：%{PATTERN_NAME:field_name}。

模式 匹配目标 示例输入 提取结果
%{COMBINEDAPACHELOG} Apache/Nginx 通用日志 192.168.1.1 - - [10/May/2025:13:55...] clientip, ident, auth, timestamp, request, httpversion, response, bytes, referrer, agent
%{IP:clientip} IPv4 / IPv6 地址 192.168.1.1 clientip = "192.168.1.1"
%{TIMESTAMP_ISO8601:ts} ISO 8601 时间戳 2025-05-07T13:55:00Z ts = "2025-05-07T13:55:00Z"
%{NUMBER:duration:float} 数值（支持类型转换） 0.042 duration = 0.042（float）
%{DATA:field} 任意非空文本（贪心） anything_here field = "anything_here"
%{GREEDYDATA:rest} 任意文本（含空，到行尾） remaining text\n rest = "remaining text"

2.4 Beats — 轻量数据采集器

Beats 是 Elastic 推出的单用途轻量数据采集代理，以最低的资源占用实现各类数据源的 可靠采集与发送。每个 Beat 专注于一种数据类型的采集，部署在业务节点上作为数据入口。

Beat 数据源 采集类型 典型端口 / 协议 资源占用
Filebeat 日志文件 日志 读取本地文件系统 极低
Metricbeat 系统 / 服务指标 指标 HTTP, Prometheus, statsd 低
Packetbeat 网络数据包 网络 libpcap 嗅探 中
Heartbeat 服务可用性 Uptime ICMP / TCP / HTTP 极低
Winlogbeat Windows 事件日志 日志 Windows Event Log API 低
Auditbeat 审计数据 审计 Linux Audit Framework 低

2.4.1 Filebeat 配置示例

以下配置演示 Filebeat 采集 Nginx 日志并发送至 Logstash（经 TLS 加密）：

filebeat.inputs:
  - type: log
    enabled: true
    paths:
      - /var/log/nginx/access.log
      - /var/log/nginx/error.log
    fields:
      service: nginx
      environment: production
    multiline:
      pattern: '^\d{4}/\d{2}/\d{2}'
      negate: true
      match: after

output.logstash:
  hosts: ["logstash.internal:5044"]
  ssl.certificate_authorities: ["/etc/filebeat/ca.crt"]
  ssl.certificate: "/etc/filebeat/client.crt"
  ssl.key: "/etc/filebeat/client.key"

logging.level: info

Beats 设计哲学： （1）每个 Beat 职责单一，降低配置复杂度；（2）Go 语言开发，无运行时依赖，二进制部署； （3）内置背压机制（Backpressure-sensitive），自动调节发送速率防止目标过载； （4）支持 elasticsearch、logstash、kafka、redis 多种输出目标；（5）模块（Module）体系提供预配置的采集模板。Filebeat 是最广泛部署的 Beat， 是日志采集的标准入口。

☞ 本节核心结论

  1. ES 是 ELK 的存储与计算核心：其倒排索引与分片架构专为海量日志的全文搜索设计， Query DSL 覆盖从简单关键词到嵌套聚合的全谱分析需求。
  2. Logstash 的 Grok 引擎是日志治理的关键：将非结构化原始日志转化为 ECS 兼容的结构化数据， 是后续分析、可视化的前提。
  3. Beats 采集器生态降低了数据接入门槛：特别是 Filebeat 的模块化配置， 可在分钟级完成常见日志类型（Nginx、MySQL、Docker 等）的采集部署。
  4. Kibana 提供"即插即用"的可视化体验：从 Discover 探索到 Dashboard 组装， 全程零代码或低代码操作，降低使用门槛。
  5. 局限性：ES 在时序指标场景不如 Prometheus 高效；大规模集群运维成本较高； Logstash 在极端吞吐下可能成为瓶颈（此时建议引入 Kafka 做缓冲层）。

Grafana + Prometheus 生态

Grafana 与 Prometheus 是云原生可观测性领域最广泛采用的开源组合。Prometheus 提供指标采集与告警能力，Grafana 作为统一可视化层对接 Prometheus、Loki、Tempo、ELK 等多数据源，共同构建覆盖 Metrics、Logs、Traces 三大信号的可观测性平台。

生态架构

Grafana 生态以 Grafana Labs 为核心，围绕 Prometheus（指标）、Loki（日志）、Tempo（追踪）三条产品线构建，配合 Mimir（长期存储）与 Pyroscope（性能分析）形成完整的 CNCF 原生可观测性栈。

Prometheus 指标系统

拉模型架构

Prometheus 采用 Pull 模型，由服务端主动轮询目标暴露的 /metrics HTTP 端点采集指标数据。相比 Push 模型，Pull 模型天然具备健康检测能力——目标宕机时采集即失败，无需额外心跳机制。

指标类型

Counter

单调递增计数器，只增不减。适用于请求总数、错误总数、任务完成数等场景。重启时归零。

只增累计

Gauge

可增可减的瞬时值。适用于内存使用率、CPU 温度、并发请求数等波动量测场景。

可增可减瞬时值

Histogram

将观测值落入可配置的桶（bucket）中，支持计算分位数。适用于请求延迟、响应体大小等分布分析。

分桶分布分析

Summary

在客户端预计算分位数（如 P50/P90/P99），直接暴露结果。适用于已知分位数需求的场景，但无法在查询时动态调整。

客户端预计算

PromQL 查询示例

每秒请求速率 — 使用 rate() 函数计算 Counter 在 5 分钟窗口内的平均每秒增长率：

rate(http_requests_total[5m])

按服务聚合 — 使用 sum by() 按服务维度聚合，观察每个服务的请求速率：

sum by(service) (rate(http_requests_total[5m]))

P99 延迟 — 使用 histogram_quantile() 从直方图桶中估算第 99 百分位的请求延迟：

histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

Grafana 可视化平台

Grafana 是统一可视化层，支持对接 Prometheus、Loki、Elasticsearch、InfluxDB、CloudWatch、Azure Monitor 等 40+ 数据源。其核心能力包括：

Dashboard

通过拖拽式面板构建交互式监控仪表盘，支持图表、表格、状态历史、地理信息等多种可视化组件。支持模板变量实现动态过滤。

Explore

临时查询界面，无需创建仪表盘即可使用 PromQL/LogQL/TraceQL 等语言探索数据。支持多数据源切换与对比分析。

Alerting

统一告警引擎，支持基于 Prometheus 规则或 Grafana 规则的告警评估。支持钉钉、Slack、PagerDuty 等 20+ 通知渠道，内置静音、聚合、分级功能。

Loki 日志聚合

Loki 是 Grafana Labs 推出的日志聚合系统，采用 标签驱动 的存储架构。日志数据通过标签（与 Prometheus 标签体系一致）进行索引，日志内容本身存储为压缩块，而非全文索引，大幅降低存储成本。

核心设计理念：仅索引元数据（标签），不索引日志内容。查询时先通过标签选择日志流，再对匹配的日志内容进行行过滤或正则匹配。

LogQL 示例

流选择器 + 行过滤 — 筛选应用 nginx 中包含 error 关键字的日志行：

{app="nginx"} |= "error"

日志速率 — 计算 nginx 日志每秒产生速率，可用于与指标系统中的错误率进行关联验证：

rate({app="nginx"}[5m])

Tempo 分布式追踪

Tempo 是 Grafana Labs 的分布式追踪后端，支持 OpenTelemetry、Jaeger、Zipkin 等多种协议的数据写入。其核心特点包括：

  • 对象存储后端：使用 S3/GCS/Azure Blob 等廉价对象存储，无需专有索引引擎
  • TraceQL 查询语言：通过 TraceQL 可以按 Span 属性、持续时间、服务名称等维度检索追踪
  • TraceID 检索：支持通过 traceID 快速定位特定请求的全链路追踪数据
  • 链路关联：与 Loki 集成，实现日志到追踪的无缝跳转——日志中携带 traceID，一键跳转至 Tempo 追踪详情

Mimir 长期存储

Mimir 是 Prometheus 的长期指标存储方案，提供水平扩展、多租户、对象存储后端（S3/GCS）等功能。核心价值在于：

  • Prometheus API 兼容：现有 Grafana 仪表盘和 PromQL 查询无需任何改造即可对接 Mimir
  • 水平扩展：通过微服务架构分离读写路径，各组件可独立扩缩容
  • 压缩与降采样：自动对历史数据进行压缩降采样，平衡存储成本与查询性能
  • 多租户隔离：支持多团队共享一套 Mimir 集群，租户间数据隔离

三大信号模型

三大信号数据模型

OTel 定义了可观测性的三大信号（Three Pillars），每种信号都有独立的数据模型和 API：

Traces 分布式追踪

核心实体为 Span，每个 Span 包含 TraceId、SpanId、ParentSpanId，通过父子关系构成调用链路。

  • TraceId：一次请求的全局唯一标识
  • SpanId：单个操作的唯一标识
  • SpanKind：Client / Server / Internal / Producer / Consumer

Metrics 指标

核心实体为 Instrument 和 MetricPoint，通过 Instrument API 创建 Counter、Histogram、Gauge 等指标类型。

  • Instrument：指标的定义，如 Counter、UpDownCounter、Histogram
  • MetricPoint：时间序列上的具体测量值
  • Exemplar：将指标与 trace 关联的样本数据

Logs 日志

核心实体为 LogRecord，支持结构化日志，可与 TraceContext 关联实现日志与追踪的联动。

  • LogRecord：包含时间戳、严重级别、消息体
  • TraceContext 注入：日志自动携带 TraceId / SpanId
  • SeverityNumber：标准化日志级别（SEVERITY_TRACE ~ SEVERITY_FATAL）

关键洞察：三大信号并非孤立存在。OTel 通过 TraceContext 将三者打通 —— 日志自动携带 TraceId 和 SpanId，指标中的 Exemplar 可关联到特定 Span，实现从指标降噪到日志定位再到链路分析的完整排查路径。

OTel Collector Pipeline

OTel Collector 是一个与语言无关的代理/网关组件，负责接收、处理和导出遥测数据。其核心架构为 pipeline 模式，由三个环节组成：

1. Receivers（接收器）

支持多种格式的输入，包括 OTLP、Jaeger、Prometheus、Zipkin、Kafka 等。最常用的是 otlp receiver，接受 gRPC 和 HTTP 两种协议。

2. Processors（处理器）

对数据进行过滤、采样、批处理、属性修改等。常用处理器有 batch（批处理）、memory_limiter（内存限制）、filter（过滤）、attributes（属性修改）等。

3. Exporters（导出器）

将处理后数据发送到后端。支持 Prometheus、Jaeger、OTLP、AWS X-Ray、Google Cloud Monitoring 等数十种目标。

以下是一个典型的 OTel Collector 配置示例：

receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
    timeout: 1s
    send_batch_size: 1024
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
  attributes:
    actions:
      - key: environment
        value: production
        action: upsert

exporters:
  otlp:
    endpoint: tempo.example.com:4317
    tls:
      insecure: false
  prometheus:
    endpoint: 0.0.0.0:8889

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch, attributes]
      exporters: [otlp]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [prometheus]

Context Propagation 与 Sampling

Context Propagation

OTel 的核心机制之一，通过在服务间传递 TraceContext 或 Baggage，将一次分布式请求的上下文信息（TraceId、SpanId、自定义键值对）沿调用链路传播。支持 W3C TraceContext 标准（traceparent 和 tracestate 头）。

  • W3C traceparent：版本号 + TraceId + SpanId + trace 标志
  • W3C tracestate：厂商扩展信息的键值对
  • Propagator 插件化支持多种格式

Sampling（采样策略）

在大量请求中只保留部分 trace 数据，以控制存储和传输成本。OTel 提供了多种采样策略：

  • Head-based：在请求入口处决定是否采样，一致性高，但无法基于运行时异常做决策
  • Tail-based：收集完整数据后在出口端分析后再决定是否保留，灵活但成本较高
  • Probabilistic：按固定概率（如 10%）随机采样
  • Rate Limiting：控制每秒采样的 trace 数量

OTLP 协议

OTLP（OpenTelemetry Protocol）是 OTel 的原生数据交换协议，支持 gRPC 和 HTTP/Protobuf 两种传输方式。OTLP 是连接 OTel SDK、Collector 和后端之间的标准协议。

gRPC 传输

基于 Protobuf 编码的二进制流，性能高，支持流式传输和双向压缩。默认端口 4317。

HTTP/Protobuf

将 Protobuf 编码数据通过 HTTP POST 发送，兼容性更好，方便在浏览器和网关场景中使用。默认端口 4318。

协议版本

OTLP 有独立的版本演进轨迹，当前稳定版本为 v1。版本号遵循 Protobuf package 命名规范（opentelemetry.proto.collector.trace.v1）。

关键结论：OTLP 的标准化意义在于 —— 从 SDK 到 Collector 再到后端，整个链路使用同一种协议和数据格式，避免了传统方案中 Trace → Jaeger Thrift、Metrics → Prometheus Text、Logs → JSON 的多协议拼凑问题。

Fluent Bit Pipeline

Fluent Bit 的数据处理流程是一个高度可配置的管道，各个阶段职责明确：

1. Input（输入）

从多种来源采集数据，包括文件尾随（tail）、系统日志（systemd）、TCP/UDP、Kubernetes 事件、Prometheus 指标等。

2. Parser（解析器）

将非结构化文本解析为结构化数据。支持正则、JSON、LTSV、Logfmt、多行日志拼接等解析模式。

3. Filter（过滤器）

对结构化记录进行修改、增强、丢弃。包括 grep（条件过滤）、modify（字段增删改）、nest（嵌套展开）、kubernetes（自动添加 K8s 元数据）等。

4. Buffer（缓冲）

使用内存 + 文件系统双重缓冲机制，保障数据不丢失并提供背压处理。

5. Routing（路由）

通过 Tag 匹配机制将不同来源的数据路由到不同输出端。

6. Output（输出）

支持 Elasticsearch、S3、Kafka、HTTP、OTLP、Prometheus、Grafana Loki 等数十种目标。

    match       kube.*
    kube_url    https://kubernetes.default.svc
    annotations On

关键结论：Fluent Bit 的设计哲学是"小而专"——它在节点级做高效的日志采集和初步处理，而非承担复杂的聚合与路由职责。在实际部署中，典型的模式是 Fluent Bit（节点采集）→ Fluentd / OTel Collector（聚合处理）→ 后端存储 的分层架构。

Jaeger：原生 OTLP 的分布式追踪

Jaeger 是 Uber 开源的分布式追踪系统，也是 CNCF 的毕业项目。随着 OTel 的普及，Jaeger 在 v2 版本中原生支持 OTLP 协议，标志着追踪领域标准的统一。

原生 OTLP 接收

Jaeger v2 可以直接通过 4317（gRPC）和 4318（HTTP）端口接收 OTLP 格式的 trace 数据，不再需要 Jaeger Thrift 协议或 Collector 做格式转换。

架构组件

包括 Agent（节点代理，已逐渐被 OTel Collector 取代）、Collector（数据接收与存储）、Query（查询 API）和 UI（Web 界面）。

存储后端

支持 Cassandra、Elasticsearch、以及通过 gRPC 插件接入自定义存储。Jaeger v2 默认使用 OpenSearch / Elasticsearch。

在标准部署中，Jaeger 通常作为 OTel Collector pipeline 的 Exporter 目标，形成 OTel SDK → OTel Collector → Jaeger 的完整链路。由于双方都使用 OTLP 协议，整条链路上不再有任何格式转换的中间环节，降低了复杂度和延迟。

Mimir

社区：Grafana Labs 主导，Cortex 继任者

架构：微服务 + 无共享（继承 Cortex）

存储后端：对象存储 + 块压缩优化

关键特性：简化运维、水平扩展、Grafana 深度集成、解决写放大

部署复杂度：较低（相对 Cortex）

关键洞察：Mimir 是 Cortex 的进化版，解决了 Cortex 严重的写放大和运维复杂度问题。Grafana Labs 的全力投入使其成为当前 Prometheus 长期存储的首选方案。Thanos 的"胶水式"集成仍适用于已有大规模 Prometheus 部署的场景，但新项目建议直接选用 Mimir。

Metrics Prometheus vs Search Elasticsearch

两者严格来说并非直接竞争对手——Prometheus 是指标采集和存储的王者，Elasticsearch 是日志搜索和分析的王者。但它们在大型可观测性平台中经常被放在一起比较。

Prometheus

核心能力：指标采集与告警

数据模型：多维 Label 模型 + PromQL

采集方式：Pull 模型，自动服务发现

不可替代性：在指标领域是事实标准，ES 无法取代其指标采集和查询能力

Elasticsearch

核心能力：全文搜索与日志分析

数据模型：倒排索引 + JSON 文档

采集方式：Push 模型，通过 Logstash / Beats 写入

不可替代性：在日志搜索和全文检索领域是标杆，Prometheus 无法取代 ES

关键洞察：两者形成了"各司其职"的格局——指标用 Prometheus，日志用 ES。真正的竞争不在工具层面，而在更高维度的生态之战：Prometheus 所在的 LGTM 生态 vs Elasticsearch 所在的 ELK 生态。

Ecosystem ELK vs LGTM vs OTel 生态

三大生态体系形成三足鼎立，分别代表了商业公司主导（Elastic / Grafana Labs）和社区标准主导（CNCF OTel）三种不同的可观测性策略。

ELK Stack

主导方：Elastic 公司

核心组件：Elasticsearch + Logstash + Kibana

核心里程碑：Elasticsearch + Logstash + Kibana 堆栈，以 ES 全文搜索为核心

最大优势：最强的搜索与分析能力，商业化成熟度高

主要劣势：组件偏重（Logstash 1GB+ 内存），License 切换争议，指标/链路能力薄弱

LGTM Stack

主导方：Grafana Labs

核心组件：Loki + Grafana + Tempo + Mimir

核心里程碑：以 Grafana 为统一面板，Loki/Tempo/Mimir 分别覆盖日志/链路/指标

最大优势：一体化体验，轻量云原生，Prometheus 原生集成

主要劣势：Loki 日志搜索能力不如 ES，Tempo 链路存储成熟度有待提升

OTel 生态

主导方：CNCF / 社区中立

核心组件：OTel 协议 + OTel Collector

核心里程碑：定义三大信号的数据模型和传输协议，成为行业标准

最大优势：标准统一，避免厂商锁定，厂商中立

主要劣势：不包含存储和可视化，需要与 ELK 或 LGTM 结合使用

关键洞察：三者的关系可以用"标准层 vs 平台层"来理解。OTel 是标准协议层（数据模型 + 采集传输），ELK 和 LGTM 是平台层（存储 + 可视化 + 告警）。实践中 OTel + LGTM 的组合越来越常见——OTel 负责统一采集，LGTM 负责存储和展示。ELK 则以其无可匹敌的搜索能力固守日志分析重场景。

5.2 互补关系

除了竞争，这些工具之间更常见的是互补协作。一个完整的可观测性平台通常是多个工具的有机组合。

Grafana + Prometheus + Loki + Tempo + Mimir

Metrics Logs Traces Viz

Grafana Labs 定义的"完整可观测性平台"组合。Prometheus 采集指标，Loki 采集日志，Tempo 采集链路，Mimir 提供指标长期存储，Grafana 统一可视化。五个组件在数据流上完全互补，形成从采集到展示的完整闭环。

OTel Collector + 任意后端

Metrics Logs Traces

OTel Collector 作为通用采集层，可以输出到任何兼容 OTel 的后端——无论是 Prometheus、Jaeger、Loki、还是 Elasticsearch。这使 OTel 成为"可观测性数据总线"，让采集层与存储层之间的绑定彻底解耦。

Fluent Bit + Elasticsearch

Logs Search

最经典的日志采集组合。Fluent Bit 的轻量采集 + Elasticsearch 的强力存储搜索，构成 ELK 生态中的高效管道。事实上 Fluent Bit 正在逐步替代 Logstash 成为 ES 生态中的默认日志采集器。

关键洞察：互补关系正在从"硬绑定"转向"松耦合"。OTel 的标准化使得采集层与存储层可以独立演进——同一套采集管道可以同时向多个后端输出。这种解耦是云原生可观测性的核心趋势，也让技术选型从"选生态"变成了"选层次"。

6. 查询语言入门详解

可观测性三大支柱——日志、指标、链路——各自拥有专用的查询语言。Elasticsearch Query DSL（JSON 风格）、PromQL（Prometheus 的函数式查询）、LogQL（Loki 的日志查询）是该领域最广泛使用的三种语言。掌握它们是构建可观测性平台的基本功。本章以"入门教程"的形式逐一拆解其完整语法与示例。

6.1 ES Query DSL

Elasticsearch 使用基于 JSON 的 Query DSL（Domain Specific Language）作为查询接口。所有查询请求体都是合法的 JSON，提交到 _search 端点。以下逐一介绍最常用的查询类型。

6.1.1 match 查询 — 全文搜索

match 是最基础的全文搜索查询。它会对查询字段执行分词（analysis），然后搜索匹配的文档。适用于日志消息、描述文本等自然语言字段。

{
  "query": {
    "match": {
      "message": "error occurred"
    }
  }
}

6.1.2 term 查询 — 精确匹配

term 用于精确值匹配，不会对查询值做分词。适合状态码、枚举值、ID 等 keyword 类型字段。

{
  "query": {
    "term": {
      "status_code": 200
    }
  }
}

6.1.3 terms 查询 — 多值匹配

terms 是 term 的多值版本，检查字段值是否在给定集合中。

{
  "query": {
    "terms": {
      "status_code": [200, 201, 304]
    }
  }
}

6.1.4 range 查询 — 范围过滤

range 用于数字或日期字段的范围过滤。支持 gt / gte / lt / lte 四种操作符。日期字段还可使用 now 和日期数学表达式。

{
  "query": {
    "range": {
      "@timestamp": {
        "gte": "now-7d",
        "lte": "now"
      }
    }
  }
}

6.1.5 bool 查询 — 组合查询

bool 是最强大的复合查询，通过四种子句组合多个条件：

  • must —— 必须匹配，贡献算分
  • filter —— 必须匹配，不计算分（可缓存，性能优）
  • must_not —— 必须不匹配
  • should —— 可选匹配，提升相关度
{
  "query": {
    "bool": {
      "must":     { "match": { "title": "error" } },
      "filter":   { "term": { "status": "active" } },
      "must_not": { "range": { "priority": { "gte": 5 } } },
      "should":   { "term": { "tag": "critical" } }
    }
  }
}

6.1.6 聚合分析（Aggregations）

ES 的聚合功能使其超越搜索，成为分析引擎。聚合分为 分桶（Bucketing）、指标（Metric）、管道（Pipeline）三类。以下是最常用的几种：

terms 聚合 — 分组统计
{
  "size": 0,
  "aggs": {
    "by_status": {
      "terms": { "field": "status_code" }
    }
  }
}
date_histogram — 时间维度聚合
{
  "aggs": {
    "over_time": {
      "date_histogram": {
        "field":    "@timestamp",
        "interval": "hour"
      }
    }
  }
}
avg / sum / cardinality — 指标聚合
{
  "aggs": {
    "avg_latency": { "avg": { "field": "latency_ms" } },
    "total_requests": { "value_count": { "field": "request_id" } },
    "unique_users": { "cardinality": { "field": "user_id" } }
  }
}

6.2 PromQL

PromQL（Prometheus Query Language）是专为时间序列数据设计的函数式查询语言。其核心概念包括 Instant Vector、Range Vector、以及丰富的聚合与运算函数。理解这些基础即可应对绝大多数监控场景。

6.2.1 Instant Vector Selector — 即时向量选择器

通过指标名 + 标签筛选器选择当前时刻的时间序列。返回每个序列的最新采样值。

http_requests_total{job="api", method="GET"}

6.2.2 Range Vector — 区间向量

在指标选择后加 [持续时间]，获取过去一段时间窗口内的所有样本点。这是计算速率、增长率的必要前提。

http_requests_total[5m]

6.2.3 rate / irate / increase — 速率计算

三者都作用于 Counter 类型指标：rate() 计算窗口内平均每秒增长率，适合长期趋势；irate() 使用窗口最后两个样本计算瞬时速率，适合短时突增；increase() 返回窗口内总增量。 

rate(http_requests_total[5m])

6.2.4 聚合操作 — by / without

用 sum / avg / min / max 等聚合函数配合 by 子句按维度汇总。

sum by(service) (rate(http_requests_total[5m]))

6.2.5 topk — 取 Top N

topk 返回指定数量内值最大的时间序列，非常适合仪表盘中的"热点"展示。

topk(3, rate(http_requests_total[5m]))

6.2.6 Histogram 分位数 — histogram_quantile

配合 Histogram 类型指标，计算请求延迟的百分位值（如 P99、P95）。这是理解服务 SLI/SLO 的关键查询。

histogram_quantile(0.99, rate(duration_bucket[5m]))

6.2.7 offset — 时间偏移

offset 允许将查询时间窗口向后偏移，用于同比对比（如当前 vs 上周同一时刻）。

http_requests_total offset 1h

6.3 LogQL

LogQL 是 Grafana Loki 的日志查询语言，语法深受 PromQL 影响，但针对日志行内容处理做了扩展。其基本结构为：日志流选择器 + 行过滤器 + 解析器/格式化器 + 区间聚合。

6.3.1 Log Stream Selector — 日志流选择器

与 PromQL 的标签选择器一致，先通过标签筛选日志流（即日志来源）。

{job="nginx", env="prod"}

6.3.2 Line Filter — 行过滤器

在流选择器后通过管道符 | 追加过滤器。支持精确包含（|=）、排除（!=）、正则匹配（|=~ 和 !~）。 

{job="nginx"} |= "error" |~ "5[0-9]{2}"

6.3.3 Parser — 解析与格式化

| json 将 JSON 格式的日志行解析为键值对，便于后续过滤与展示。| logfmt 处理 logfmt 格式。| line_format 可重写日志行内容。 

{app="web"} | json
| line_format "{{.method}} {{.status}}"

6.3.4 Range Aggregation — 区间聚合

与 PromQL 的 Range Vector 类似，LogQL 也支持对日志条目进行速率计算，实现日志指标的等价能力。

rate({app="nginx"}[5m])

6.4 三种语言特性对比

下表从数据模型、查询入口、过滤方式、聚合能力等多个维度横向对比三种语言，帮助读者根据场景选择合适工具。

6.5 学习要点

ES Query DSL

  • JSON 格式，适合机器生成和解析
  • match 作分词搜索，term 作精确查找
  • bool 四种子句是组合查询核心
  • 聚合（Aggs）将 ES 从搜索引擎升级为分析引擎

PromQL

  • 纯函数式风格，支持链式运算
  • 区分 Instant Vector 和 Range Vector
  • rate / irate / increase 三选一需理解场景差异
  • histogram_quantile 是 SLO 监控的基础

LogQL

  • 管道式语法，每一步处理一行日志
  • 流选择器先筛来源，行过滤器再筛内容
  • | json / | logfmt 将非结构化日志结构化
  • LogQL 的区间聚合使其兼具指标查询能力

速记口诀：

  • ES DSL —— JSON 写查询，match 做搜索，term 做匹配，bool 搭积木，aggs 出统计
  • PromQL —— 指标名 + 标签选数据，函数 + 括号做变换，by 分组，rate 算速率，histogram_quantile 求分位
  • LogQL —— 大括号选流，管道符过滤，json/logfmt 解析，rate 算日志指标

部署模式与总结建议

三种部署模式

根据团队的规模、运维能力和业务需求，可观测性基础设施通常采用以下三种部署模式之一。各模式在成本、复杂度、可扩展性之间存在明确权衡。

轻量方案

适合个人开发者或初创团队

指标场景： Prometheus + Grafana

日志场景： ELK Stack 单节点部署

单机部署、零容器编排、运维成本最低，适合日均处理 TB 级以下数据量的场景。

企业方案

适合中大型团队或对可靠性的要求高的场景

高可用日志： ELK Stack + Kafka 缓冲层

全栈可观测： LGTM Stack（Loki + Grafana + Tempo + Mimir）

多节点集群、消息队列削峰填谷、数据副本与故障转移，适合日均 PB 级数据量。

云原生方案

适合 Kubernetes 集群或多云架构

采集层： OpenTelemetry Collector

后端： 可替换（Prometheus / Loki / Tempo / 第三方 SaaS）

声明式部署、自动发现与弹性伸缩，通过 OTel 协议解耦采集与存储，是面向未来的架构。

以下表格总结了不同业务场景下的推荐方案与核心理由，帮助团队快速做出技术决策。

场景 推荐方案 理由
指标 + 告警 Prometheus + Grafana 指标领域事实标准，查询语言（PromQL）成熟，告警规则生态完善，社区活跃度最高。
日志 + 全文搜索 ELK Stack Elasticsearch 的全文搜索能力至今无可替代，Logstash 管道生态完善，Kibana 可视化丰富。

未来趋势

可观测性领域正在经历快速演进，以下趋势将深刻影响未来 3-5 年的技术选型与架构设计。

标准 OpenTelemetry 统一标准

OTel 已成为采集与传输层的共识标准，正在逐步统一三大信号的采集协议与数据模型。CNCF 生态中的新生工具几乎全部原生支持 OTel 协议。

采集 eBPF 无侵入采集

eBPF 技术使内核级别的无侵入数据采集成为可能，无需修改应用代码即可获取网络、文件系统、性能等指标。Pixie、Cilium 等项目已率先落地。

智能 AIOps 智能分析

基于机器学习的异常检测、根因分析和智能告警正在从实验走向生产。AIOps 将显著降低运维人员处理海量告警的认知负担。

融合 统一信号替代三支柱

指标、日志、链路三大信号的界限正在模糊。结构化日志可直接作为指标来源，链路上下文可关联日志。未来可观测性将基于关联事件而非孤立信号。

核心结论

可观测性技术选型没有银弹。轻量模式适合快速起步，企业模式适用于规模运营，云原生模式是面向未来的最佳选择。无论选择何种路径，OpenTelemetry 都应作为数据采集的首选标准——它提供了最大的后端灵活性和最低的迁移成本。
