📦 ES · Index / Document / Mapping + CRUD 实战

在 Kibana Dev Tools → Console 中执行。先建再查再删，10 分钟从零到会。

创建索引 + 写入

# 1. 建索引（不指定 mapping 的话 ES 自动推断） PUT /shop # 2. 写入文档（自动推断字段类型） POST /shop/_doc { "name": "笔记本电脑", "price": 6999, "stock": 100, "tags": ["电子", "办公"], "created_at": "2026-05-08" } # 3. 批量写入（效率更高） POST /shop/_bulk {"index":{}} {"name":"手机","price":4999,"stock":200} {"index":{}} {"name":"平板","price":2999,"stock":150}

查询

# 4. 搜索全部 GET /shop/_search { "query": { "match_all": {} } } # 5. 搜"笔记本" GET /shop/_search { "query": { "match": { "name": "笔记本" } } } # 6. 价格范围 GET /shop/_search { "query": { "range": { "price": { "gte": 2000, "lte": 6000 } } } }

更新 + 删除

# 7. 更新字段 POST /shop/_update/文档ID { "doc": { "stock": 80 } } # 8. 删除文档 DELETE /shop/_doc/文档ID # 9. 按条件删除 POST /shop/_delete_by_query { "query": { "match": { "name": "平板" } } } # 10. 删除索引 DELETE /shop

mapping 手动定义（推荐）

# 手动定义字段类型，避免自动推断错误 PUT /products { "mappings": { "properties": { "name": { "type": "text" }, "price": { "type": "integer" }, "stock": { "type": "integer" }, "tags": { "type": "keyword" }, "created_at": { "type": "date" } } } } # text=分词 | keyword=精确匹配 | integer=整数 | date=时间
💡 刚上手在 Dev Tools 里练习 POST/PUT/GET/DELETE 就够了。写入→映射→搜索是核心三部曲。

🔍 ES Query DSL · 7 种查询完整示例

① match（分词搜索）

GET /logs/_search { "query": { "match": { "message": "error connection timeout" } }} # "error connection timeout" 分词为 [error,connection,timeout] # 含任一词即命中，按匹配度评分排序

② match_phrase（短语匹配）

GET /logs/_search { "query": { "match_phrase": { "message": "connection timeout" } }} # "connection timeout" 顺序和距离必须一致

③ term（精确匹配）

GET /logs/_search { "query": { "term": { "level": "error" } }} # 不经过分词器，keyword 字段专用 # 常用于 status_code、level、env 等枚举字段

④ terms（多值匹配）

GET /logs/_search { "query": { "terms": { "level": ["error","warning"] } }} # 匹配任意一个就算命中

⑤ range（范围查询）

GET /logs/_search { "query": { "range": { "response_time": { "gt": 1000, "lte": 5000 }, "@timestamp": { "gte": "now-1h" } } }} # gt > | gte >= | lt < | lte <= # 时间支持 now-1h now/d 等自然语法

⑥ exists（字段存在性）

GET /logs/_search { "query": { "exists": { "field": "error_stacktrace" } }} # 筛选 error_stacktrace 非空的文档

⑦ bool（组合查询核心）

GET /logs/_search { "query": { "bool": { "must": [{ "match": {"message":"error"} }], "filter": [{ "term": {"level":"error"} }], "must_not": [{ "term": {"service":"health"} }], "should": [{ "match": {"message":"urgent"} }] } }} # must=参与评分 filter=不评分可缓存 # must_not=排除 should=提升评分非必须

📊 ES 聚合 Analy· 5 种聚合 + 嵌套实战

① terms（分组计数）

GET /logs/_search { "size":0, "aggs": { "by_level": { "terms": { "field":"level", "size":5 } } }} # → error:234, warn:567, info:12345

② date_histogram（时间柱状图）

GET /logs/_search { "size":0, "aggs": { "hourly": { "date_histogram": { "field":"@timestamp", "calendar_interval": "hour" } } }} # calendar=月/年 fixed=5m/2h 精确间隔

③ avg/sum/stats（统计量）

GET /logs/_search { "size":0, "aggs": { "resp_stats": { "stats": { "field":"response_time" } } }} # stats 同时返回 count/min/max/avg/sum

④ cardinality（去重计数）

GET /logs/_search { "size":0, "aggs": { "unique_ips": { "cardinality": { "field":"client_ip" } } }} # ≈ SELECT COUNT(DISTINCT client_ip)

⑤ percentiles（百分位）

GET /logs/_search { "size":0, "aggs": { "p99": { "percentiles": { "field":"response_time", "percents":[50,95,99] } } }} # P99=500ms 说明 99% 请求在 500ms 内

⑥ 嵌套：按服务分组后算 P99

GET /logs/_search { "size":0, "aggs": { "by_service": { "terms": { "field":"service.keyword" }, "aggs": { "avg_resp": { "avg": {"field":"response_time"} }, "p99_resp": { "percentiles": {"field":"response_time","percents":[99]} }, "hourly": { "date_histogram": {"field":"@timestamp","fixed_interval":"1h"} } } } }} # 第 1 层分组，第 2 层每组分别算统计 # → api: avg=120ms p99=450ms hourly=[...]
💡 嵌套聚合流程：先想清楚"按什么分组"，再想"每组算什么"。terms/date_histogram 是分组器，avg/sum/cardinality/percentiles 是统计器，套在一起就是多维分析。

📊 Prometheus · 指标类型 + Node Exporter 实操

4 种指标类型

类型特性常见函数例
Counter只增不减rate() increase()http_requests_total
Gauge可增可减直接看, delta()node_memory_usage
Histogram分桶统计histogram_quantile()duration_seconds_bucket
Summary预算分位直接看rpc_duration

Node Exporter 启动

docker run -d --name node_exporter \ -p 9100:9100 \ prom/node-exporter # 每次采集 ~300 个指标 # CPU/内存/磁盘/网络/文件系统/进程 全覆盖

Node Exporter 常用指标

# CPU node_cpu_seconds_total{mode="idle"} node_load1 / node_load5 / node_load15 # 内存 node_memory_MemTotal_bytes node_memory_MemFree_bytes node_memory_Buffers_bytes # 磁盘 node_filesystem_size_bytes{mountpoint="/"} node_filesystem_avail_bytes{mountpoint="/"} # 网络 node_network_receive_bytes_total node_network_transmit_bytes_total

实战：常见的 PromQL 查询

# CPU 使用率 100 - avg by(instance) ( rate(node_cpu_seconds_total{mode="idle"}[5m]) ) * 100 # 内存使用率 (1 - node_memory_MemFree_bytes / node_memory_MemTotal_bytes) * 100 # 磁盘使用率 (1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100 # 网络带宽 rate(node_network_receive_bytes_total[5m]) # 磁盘 IO rate(node_disk_io_time_seconds_total[5m])

❌ 新手最常见的错误

  • 直接看 Counter：http_requests_total 一直增长看不出趋势 → 必须用 rate()
  • 忘写标签：node_memory_MemTotal_bytes 可能返回多个实例 → 加 {instance="..."}
  • Range Vector 写错：rate(http_requests_total[5m]) 必须有 [时间]
  • 标签大小写：job="api" 和 job="API" 不同

🔗 OpenTelemetry · 为什么 + 架构 + 配置

为什么需要 OTel？

❌ 没 OTel 之前：应用里混着 Jaeger API（trace）+ Prometheus 库（metrics）+ logging（日志），三个库三种配置。想换后端要改代码。

✅ 有 OTel 以后：一套 API 覆盖三种信号。换后端只改 Collector 配置，不碰业务代码。TraceID 自动注入日志，指标关联 Trace。

🔧 OTel SDK · 从自动埋点到手动控制

自动埋点（推荐，一行启动）

# 安装 pip install opentelemetry-instrumentation \ opentelemetry-instrumentation-flask \ opentelemetry-instrumentation-requests # 一行启动全部自动拦截 # Flask/requests/DB driver 等自动创建 span opentelemetry-instrument \ --traces_exporter otlp \ --metrics_exporter otlp \ --service_name my-app \ python app.py # 环境变量替代参数 export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4317 export OTEL_SERVICE_NAME=my-app opentelemetry-instrument python app.py

手动埋点（精细控制）

from opentelemetry import trace tracer = trace.get_tracer(__name__) with tracer.start_as_current_span("query_db") as span: # 加自定义属性 span.set_attribute("db.query", "SELECT * FROM users") span.set_attribute("db.rows", 42) span.set_attribute("db.duration_ms", 350) # 加事件 span.add_event("db:query_start") # ... 业务代码 ... span.add_event("db:query_complete") # 记录错误 span.set_status(trace.Status(trace.StatusCode.ERROR)) span.record_exception(e)

💨 Fluent Bit · 架构 + 配置文件详解

核心优势

C 语言编写，空闲内存 ~650KB（Fluentd ~40MB）。性能是 Fluentd 的 10-40 倍。支持 Grok 正则解析（200+ 内置模式）。K8s DaemonSet 标配。

常改文件

文件改了会怎样
fluent-bit.conf整个管道配置——改完重启生效
parsers.conf日志解析规则——改了不重启，自动加载

启动方式

💨 Fluent Bit · K8s 部署 + 生产最佳实践

K8s DaemonSet 配置

# fluent-bit-config.yaml apiVersion: v1 kind: ConfigMap metadata: name: fluent-bit-config namespace: logging data: fluent-bit.conf: | [SERVICE] flush 5 log_level info parsers_file parsers.conf [INPUT] name tail path /var/log/containers/*.log parser cri tag kube.* mem_buf_limit 50MB skip_long_lines On [FILTER] name kubernetes match kube.* merge_log On keep_log On k8s-logging.parser On labels On annotations On [OUTPUT] name es match * host elasticsearch.logging port 9200 index k8s-logs-${DATE} retry_limit 2 buffer_size 2MB --- apiVersion: apps/v1 kind: DaemonSet spec: template: spec: containers: - name: fluent-bit image: cr.fluentbit.io/fluent/fluent-bit:latest volumeMounts: - name: config mountPath: /fluent-bit/etc/ - name: varlog mountPath: /var/log - name: docker mountPath: /var/lib/docker/containers volumes: - name: config configMap: { name: fluent-bit-config } - name: varlog hostPath: { path: /var/log } - name: docker hostPath: { path: /var/lib/docker/containers }

生产最佳实践

内存管理

  • mem_buf_limit 设每个 input 上限（推荐 50MB）
  • 超出时日志暂存到文件 system buffer
  • Fluent Bit 几乎不会 OOM，这是 vs Logstash 的核心优势

性能调优

  • flush 5 每 5 秒刷一次，日志实时性要求高可改 1
  • storage.total_limit_size 1G 限制总缓冲区大小
  • net.keepalive on 复用连接提升吞吐

常见问题

  • 日志没进 ES：先加 [OUTPUT] name stdout 确认 FB 收到日志
  • 内存飙高：检查 ES 是否可写，ES 挂了 FB 会缓冲
  • 日志格式不对：换 parser（cri/json/xyz），用 @TYPE 测试
  • ES 索引太多：用 ILM（Index Lifecycle Management）自动管理
