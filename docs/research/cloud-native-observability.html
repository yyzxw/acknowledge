📊 第 1 章 · 可观测性三大支柱

可观测性（Observability）源于控制论，指"通过系统外部输出推断内部状态的能力"。在云原生领域，通过指标 (Metrics)、日志 (Logs)、链路追踪 (Traces) 三种数据来诊断分布式系统。

Metrics 指标

数据类型：数值聚合
粒度：粗（聚合值）
存储成本：低
典型用途：告警触发、趋势分析、SLO

Logs 日志

数据类型：文本事件
粒度：细（原始文本）
存储成本：高
典型用途：根因排查、审计合规

Traces 追踪

数据类型：请求生命周期
粒度：中（Span 级）
存储成本：中
典型用途：服务依赖、性能瓶颈分析

💡 可观测性 vs 监控：监控告诉你系统"出了故障"，可观测性帮你"找到原因"。真正的价值在于信号关联——从指标异常发现故障 → 从日志定位根因 → 从追踪追溯完整请求路径。当前趋势正从"三支柱"走向"统一信号"。

📝 ES Query DSL — 6 种基础查询

1. match（分词全文搜索）

GET /logs/_search { "query": { "match": { "message": "error occurred" } } } # "error occurred" 被分词为 [error, occurred] # 匹配包含任一词的文档

2. term（精确匹配，不分词）

GET /logs/_search { "query": { "term": { "status_code": 200 } } } # 精确匹配 status_code=200 # 适合 keyword 字段和数值

3. terms（多值精确匹配）

GET /logs/_search { "query": { "terms": { "status_code": [200, 201, 304] } } } # 匹配任意一个值即可

4. range（范围过滤）

GET /logs/_search { "query": { "range": { "@timestamp": { "gte": "now-7d", "lte": "now" }, "response_time": { "gt": 1000 } } } } # gte ≥ lte ≤ gt > lt <

5. exists（字段存在性检查）

GET /logs/_search { "query": { "exists": { "field": "error_stacktrace" } } } # 筛选包含 error_stacktrace 字段的文档

6. wildcard / regexp（通配符 / 正则）

# 通配符 GET /logs/_search { "query": { "wildcard": { "message": "error*" } } } # 正则 GET /logs/_search { "query": { "regexp": { "message": "5[0-9]{2}" } } }

🔧 ES Query DSL — bool 组合查询

bool 是 ES 最核心的查询容器，包含 4 种子句，可任意组合嵌套。

must（必须匹配，参与评分）

"must": [ { "match": { "title": "error" } }, { "match": { "content": "database" } } ] # 类似 AND，文档必须满足所有条件

filter（必须匹配，不参与评分）

"filter": [ { "term": { "status": "active" } }, { "range": { "response_time": { "lte": 500 } } } ] # 不计算 _score，性能更好，可缓存

should（应该匹配，提升评分）

"should": [ { "term": { "tag": "critical" } }, { "match": { "message": "urgent" } } ] # 不强制匹配，但匹配越多评分越高 # 搭配 minimum_should_match 使用

must_not（排除匹配）

"must_not": [ { "term": { "level": "debug" } }, { "range": { "priority": { "gte": 8 } } } ] # 排除所有 debug 日志 # 和 filter 一样不参与评分
💡 实战组合：搜索最近 1 小时内 status≥400 且 response_time>1000ms 的活跃请求，排除已知的定时任务。

📊 ES Query DSL — 5 种聚合分析

聚合（Aggregation）将 ES 从搜索引擎升级为分析引擎。常在 Dev Tools 中调试，再嵌入 Dashboard。

1. terms（分组计数）

GET /logs/_search { "size": 0, "aggs": { "top_status": { "terms": { "field": "status_code", "size": 5 } } } } # → 200: 12345次, 404: 234次, 500: 56次

2. date_histogram（时间柱状图）

GET /logs/_search { "aggs": { "hourly": { "date_histogram": { "field": "@timestamp", "calendar_interval": "hour" } } } } # calendar_interval: month/quarter/year # fixed_interval: 5m/2h（固定间隔）

3. avg / sum / stats（统计）

GET /logs/_search { "aggs": { "avg_response": { "avg": { "field": "response_time" } }, "stats_response": { "stats": { "field": "response_time" } } } } # stats 同时返回 count/min/max/avg/sum

4. cardinality（去重计数）

GET /logs/_search { "aggs": { "unique_users": { "cardinality": { "field": "user_id" } } } } # ≈ SELECT COUNT(DISTINCT user_id)

5. percentiles（百分位）

GET /logs/_search { "aggs": { "p99_latency": { "percentiles": { "field": "response_time", "percents": [50, 95, 99] } } } }

🧩 ES 嵌套聚合实战

聚合可以嵌套：外层分组 → 内层统计，实现"分组后每组分别算统计"。

按状态码分组 + 延迟统计

GET /logs/_search { "size": 0, "aggs": { "by_status": { "terms": { "field": "status_code" }, "aggs": { "avg_response": { "avg": { "field": "response_time" } }, "p99_response": { "percentiles": { "field": "response_time", "percents": [99] } }, "over_time": { "date_histogram": { "field": "@timestamp", "fixed_interval": "1h" } } } } } } # 结果分层： # 200 → avg=120ms, p99=500ms, hourly=[...] # 500 → avg=3200ms, p99=8000ms, hourly=[...]

多维度下钻分析

GET /nginx-logs/_search { "size": 0, "aggs": { "by_endpoint": { "terms": { "field": "uri.keyword", "size": 10 }, "aggs": { "by_status": { "terms": { "field": "status_code" }, "aggs": { "avg_latency": { "avg": { "field": "latency_ms" } } } } } } } } # 每个 URI → 各状态码次数 → 平均延迟 # Dev Tools 中写好，直接贴进 Kibana Lens
💡 Dev Tools 使用技巧：在 Kibana 左侧 Dev Tools → Console 里直接写这些查询测试，Ctrl+Enter 执行。自动补全很方便——输入 GET / 按 Tab 列出所有索引。

🖥️ Kibana UI 三步实操

访问 http://localhost:5601，左侧导航栏是核心入口。

Step 1: 创建 Data View

  1. 左侧菜单 → Stack Management → Data Views
  2. 点击 Create data view
  3. Name 随便填，Index pattern 填 logs-*（匹配 ES 中 logs-2025.01.01 这类索引）
  4. Timestamp field 选 @timestamp
  5. 点 Save 保存

Step 2: Discover 搜日志

  1. 左侧菜单 → Discover
  2. 顶部选刚才创建的 Data View
  3. 搜索栏输入 KQL：status: >= 400 and response_time > 1000
  4. 右上角选时间范围 Last 15 minutes
  5. 右侧显示时间轴分布和文档列表
  6. 点击任一文档展开所有字段查看详情

Step 3: Dashboard + Lens

  1. 左侧 → Dashboard → Create dashboard
  2. 点 Create visualization 进入 Lens
  3. 拖 @timestamp 到 X 轴，拖 Count of records 到 Y 轴
  4. 拖 status_code 到 Breakdown 按状态码着色
  5. 右上角 Save and return 保存到仪表盘

🔧 排错锦囊

  • 搜不到数据：先检查时间范围（最常见原因），再确认 Data View 的索引模式匹配
  • 想调试查询：Dev Tools 直接写 ES API，看 JSON 返回
  • 字段没出现：刷新字段列表（Discover 右上角刷新按钮）
  • 数据不更新：页面右上角 Refresh 设为 5s 或手动刷新

完整 Pipeline 配置

📝 PromQL — Instant Vector + Range Vector

Instant Vector（即时向量）

# 最基础查询：选择所有匹配的即时值 http_requests_total # 返回：所有时间序列的当前最新值 # 带标签过滤：{label="value"} http_requests_total{job="api-server"} http_requests_total{job="api", method="GET"} # 标签匹配运算符： # = 等于 != 不等于 # =~ 正则匹配 !~ 正则排除 http_requests_total{job=~"api|web", status=~"5[0-9]{2}"} # 空标签选择：选择所有 {__name__=~".+"} # 所有指标 {job="nginx"} # 某 job 的所有指标

Range Vector（区间向量）

# 时间范围：[5m] [1h] [30s] [1d] # m=分钟 h=小时 s=秒 d=天 w=周 y=年 http_requests_total[5m] # 返回：过去 5 分钟内的所有样本值 # 注意：Range Vector 不能直接画图，需要配合函数 # offset：时间偏移 http_requests_total offset 1h # 对比当前和 1 小时前的数据 http_requests_total[5m] offset 1d # 昨天同一时刻的 5 分钟数据

关键函数

rate(http_requests_total[5m]) # 每秒增长率（最常用！） irate(http_requests_total[5m]) # 瞬时增长率（灵敏度更高） increase(http_requests_total[1h]) # 过去 1 小时的增量 delta(cpu_temperature_celsius[2h]) # Gauge 类型的变化量
💡 rate 是最常用的函数：Counter 类型指标必须用 rate()/irate()/increase() 处理才能有意义。直接看 Counter 值会一直增长，看不到趋势。

📝 PromQL — 聚合 + 运算 + histogrom_quantile

聚合操作符

# 按标签分组聚合 sum by(service) (rate(http_requests_total[5m])) # → service="api": 120qps # service="web": 200qps # 不分组 sum(rate(http_requests_total[5m])) # 其他聚合函数： # avg/max/min/count/stddev by(...) # topk(3, ...) 取前 3 # bottomk(3, ...) 取后 3 # quantile(0.95, ...) 聚合分位 # 常用模式： # 各服务错误率（带除法） sum by(service) (rate(http_requests_total{status=~"5.."}[5m])) / sum by(service) (rate(http_requests_total[5m])) * 100

histogram_quantile（P99 延迟）

# 前提：应用暴露了 Histogram 指标 # request_duration_seconds_bucket{le="0.1"} # request_duration_seconds_bucket{le="0.5"} # request_duration_seconds_bucket{le="1.0"} # request_duration_seconds_bucket{le="+Inf"} # request_duration_seconds_count # request_duration_seconds_sum # P99 延迟查询 histogram_quantile(0.99, rate(request_duration_seconds_bucket[5m]) ) # 按服务分组 histogram_quantile(0.99, sum by(service, le) ( rate(request_duration_seconds_bucket[5m]) ) ) # 平均延迟（= sum / count） request_duration_seconds_sum / request_duration_seconds_count

二元运算符

# 算术: + - * / ^ % # 比较: == != > < >= <= # bool 模式: cpu > bool 0.8 (返回 0 或 1) # 逻辑: and or unless (cpu_usage > 0.8) and (memory_usage > 0.9) # 同时高 CPU 和高内存的服务

📈 Grafana — 从零建 Dashboard

  2. 搜索 Prometheus 并选中

Step 2: 创建 Dashboard

  1. 左侧 + 图标 → New Dashboard
  2. 点 Add visualization
  3. 选择刚才配的 Prometheus 数据源

  1. Dashboard 设置 → Variables → Add variable
  2. Name: service, Type: Query
  3. Query: label_values(up, job)（自动列出所有 job）
  4. Panels 的 PromQL 中引用：rate(http_requests_total{job="$service"}[5m])
  5. 顶部出现下拉菜单，选不同 service 自动切换数据

🎯 告警配置

  1. 左侧铃铛图标 → Alerting → Alert rules
  2. 点 New alert rule
  3. 选数据源和查询
  4. 条件：WHEN last() OF query(A, 5m) IS ABOVE 0
  5. 通知：选 Slack/Email/Webhook

  3. Instrumentation — 自动/手动埋点（自动：拦截 HTTP 库、DB 驱动等）
  4. Collector — 接收 → 处理 → 转发
💡 OTel 的目标是"write once, ship anywhere"。你的代码只需要对接 OTel SDK，想换后端（Jaeger/Prometheus/ES/Grafana Cloud）只需改 Collector 配置，不用改业务代码。

🔧 OTel SDK 使用（Python 示例）

1. 手动 Instrumentation

🎯 OTel 采样策略

在数据量很大时，采样（Sampling）是控制成本的必要手段。OTel 支持多种采样策略，通常在 Collector 或 SDK 中配置。

1. Head Sampling（头部采样）

在 SDK 端决定采样，请求开始时决定是否记录 trace。优点是简单，缺点是无法基于完整 trace 信息做决策。

# SDK 端配置 from opentelemetry.sdk.trace.sampling import ( ParentBasedTraceIdRatio ) # 按比例采样 10% sampler = ParentBasedTraceIdRatio(0.1)

2. Tail Sampling（尾部采样）

在 Collector 端延迟决策。等 trace 的所有 span 到齐后再决定采不采样。可以基于结果做精细化决策。

# Collector 配置 processors: tail_sampling: decision_wait: 30s policies: - name: errors type: status_code config: { status_code: ERROR } - name: slow type: latency config: { threshold_ms: 1000 }

3. Probabilistic（概率采样）

按固定比例采样，最简单的策略。

processors: probabilistic_sampler: sampling_percentage: 10 # 10%

4. Rate Limiting（速率限制）

限制每秒采样量，避免突发流量打爆后端。

processors: rate_limiting: spans_per_second: 100
💡 推荐组合：SDK 端做 Head Sampling（如 100%），Collector 端做 Tail Sampling（保留所有错误和慢 trace，其余按比例采样）。这样不错过问题，又控制成本。

核心操作

  1. 打开 Jaeger UI（默认 :16686）或通过 Grafana
  2. 按 Service 名搜索：选 service → 点 Find Traces
  3. 看瀑布图：每个 span 显示操作名和耗时
  4. 红色 = 错误 span，长条 = 慢 span
  5. 点击 span 看详情：标签、日志、进程信息

otel-collector.yml: exporters: otlp: endpoint: "jaeger:4317" tls: { insecure: true } # Jaeger v2 原生支持 OTLP # 不再需要 Jaeger Thrift 协议 # 一条管道从 SDK→Collector→Jaeger

🔄 第 6 章 · 项目关系与选型

⚔️ 竞争关系

  • Fluent Bit vs Logstash: 内存 ~650KB vs 1GB+，性能 10-40x 差距。轻量场景 Fluent Bit，复杂 Pipeline 用 Logstash
  • OTel Collector vs Fluent Bit: OTel 统一三种信号，Fluent Bit 专精日志。v3+ FB 也开始支持 Traces/Metrics
  • Prometheus vs ES: 指标 vs 搜索，定位完全不同，更多是互补
  • Kibana vs Grafana: Kibana 绑定 ES，Grafana 对接多数据源。技术上互补，企业常同时使用

🤝 互补关系

  • Prometheus + Grafana: 黄金组合，指标采集 + 可视化
  • OTel + 任意后端: OTel 是通用采集层，输出到 Jaeger/Prometheus/ES
  • Fluent Bit + ES: 日志采集 + 存储搜索的经典搭配
  • OTel + Jaeger: 天然集成，OTel SDK 采集 → Jaeger 存储展示
  • Grafana + ES: Grafana 作为 ES 的增强可视化层，比 Kibana 灵活
场景推荐方案说明
指标 + 告警Prometheus + Grafana最成熟生态，社区最活跃
日志 + 全文搜索ELK StackES 的全文搜索不可替代
全栈可观测（新项目）OTel + Grafana + Prometheus现代化方案、统一采集
已有 ES扩展 ES + Grafana降低学习成本
分布式追踪OTel + JaegerCNCF 标准组合
