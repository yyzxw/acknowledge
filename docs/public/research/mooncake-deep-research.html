01

项目概述与定位

Mooncake 是 Moonshot AI（Kimi）开发的 LLM 推理服务平台，其核心创新在于提出了"以 KVCache 为中心的分离式架构"（KVCache-centric disaggregated architecture）。这一架构不仅将 prefill（预填充）和 decode（解码）阶段分离到不同集群，更关键的是将 GPU 集群中大量闲置的 CPU、DRAM、SSD 和 RDMA 资源整合为一个统一的分布式 KVCache 池。[1][2]

2025 年 2 月，该论文在 USENIX FAST 2025 会议上获得 Erik Riedel Best Paper Award，标志着学术界对其技术贡献的认可。[11] 2026 年 2 月，Mooncake 正式加入 PyTorch 生态系统，成为 PyTorch 官方推荐的 KVCache 基础设施。[7]

核心问题

在大模型推理服务中，KVCache 的存储和传输已成为制约吞吐量和延迟的瓶颈。传统的单体推理架构将 prefill 和 decode 耦合在同一 GPU 上，导致 GPU 计算资源利用率低下。Mooncake 通过分离式架构，将 KVCache 从"计算的附属品"提升为"一等公民"。

整体架构分析

四层架构设计

Mooncake 的架构由四个核心组件构成，形成一个层次化的系统：[1][6]

Transfer Engine（传输层）

底层数据传输层，提供统一的批量数据传输接口。屏蔽底层网络协议差异，使上层组件无需关心数据是通过 RDMA、TCP 还是 CXL 传输的。

Mooncake Store（存储层）

分布式 KVCache 存储引擎，所有 KVCache 以分页块形式存储在分布式缓存池中，块大小通常为 16-512 个 token，支持多副本和去重。

Conductor（调度层）

全局调度器，维护全局前缀树，计算请求与节点缓存的重叠分数，通过结合实时节点负载的成本函数选择最优节点。

P2P Store（去中心化存储）

基于 Transfer Engine 构建的去中心化存储系统，专注于集群节点间临时对象（如 checkpoint 文件）的共享，使用 etcd 存储全局元数据。

Transfer Engine：统一传输层

Transfer Engine 是 Mooncake 最核心的基础设施组件，其设计哲学是"一次编写，到处传输"。通过 MultiTransport 类实现了协议无关的传输抽象，传输选择基于目标段的协议元数据自动完成。[6][13]

性能数据

拓扑感知路径选择是 Transfer Engine 的关键优化。它通过扫描 /sys/devices/system/node 发现 NUMA 节点，结合 cudaDeviceGetPCIBusId 获取 GPU 的 PCI 总线 ID，计算 PCI 距离和 NUMA 节点亲和度，选择距离最近的 HCA 设备。[1]

零拷贝传输通过 GPUDirect RDMA，数据可以直接从 GPU 内存传输到远程 GPU 内存，无需经过 CPU 中转。vLLM 博客数据显示，MooncakeTransferEngineConnector 使用 RDMA 仅需约 14 ms（TCP 约 810 ms），加速比达 58x。[8]

04

Mooncake Store：分布式 KVCache 引擎

Mooncake Store 的架构设计围绕三个核心目标：高可用、高性能和易扩展。[6][18]

多副本机制

ReplicateConfig 结构支持配置副本数量、软硬 pin 策略、首选 segment 等参数。三种副本类型覆盖不同存储层级：

MEMORY 副本

内存副本，通过 AllocatedBuffer 管理，访问速度最快，适用于热数据。

DISK 副本

磁盘副本，支持 FilePerKey、Bucket、OffsetAllocator 三种后端，适用于温数据。

LOCAL_DISK 副本

本地磁盘副本，client_id + transport_endpoint 标识，适用于冷数据。

分配策略与淘汰机制

分配策略：RandomAllocationStrategy 保证不同副本在不同 segment 上；FreeRatioFirstAllocationStrategy 采样 2N 个候选 segment，按空闲率排序选最优。Best-effort 语义确保当请求数量的副本无法满足时，尽可能多地分配。[6]

淘汰策略实现为 near-LRU：BatchEvict 方法有两轮淘汰，第一轮只淘汰无 soft pin 的对象，第二轮在必要时淘汰 soft pinned 的对象。

元数据管理支持多种后端：etcd、Redis、K8s Lease、HTTP 元数据服务器。MasterService 采用 1024 个分片的元数据存储，使用 SharedMutex 实现读写分离。[6]

高可用机制包括：etcd 作为 HA 后端、Snapshot/Restore 机制（fork 子进程序列化）、Hot Standby 状态机、分布式元数据分片、Client 心跳监控。

ObjectDataType 分类

Mooncake Store 支持按数据类型存储：KVCACHE、TENSOR、WEIGHT、SAMPLE、ACTIVATION、GRADIENT、OPTIMIZER_STATE、METADATA、GENERAL，为未来类型感知策略奠定基础。

05

Conductor：全局调度器设计

Conductor 的核心职责是在最大化有效吞吐量的同时满足延迟相关的 SLO。与传统基于请求数量的负载均衡不同，Mooncake 的调度考虑了更多维度。[6][1]

Cache-aware Prefill 调度

Conductor 维护一个全局前缀树（global prefix tree），计算请求与节点缓存的重叠分数。调度决策不仅考虑负载，还考虑：

  • 前缀缓存命中长度：优先将请求路由到具有更长前缀缓存的 prefill 实例
  • 可复用 KVCache 块分布：考虑 KVCache 块在集群中的分布
  • 排队时间：结合前缀缓存带来的 prefill 时间和本地排队时间

Load-balance Decode 调度使用以下负载评分公式：

load_score = current_batch_size + k * waiting_queue_length

SLO 感知调度与早期拒绝

定义 l_ttft 和 l_tbt 分别为 TTFT（Time To First Token）和 TBT（Time Between Tokens）的 SLO 约束，通过比较实例上预测的最大 TTFT/TBT 与 SLO 约束来确定负载。[1]

预测式早期拒绝策略解决过载场景下的负载波动问题。核心思想是预测 prefill 阶段完成后的 decode 负载，据此决定是否接受请求。这包括请求级预测（预测每个请求的未知输出长度）和系统级预测（预测未来时间段的整体系统负载）。

开源状态

Conductor 目前以 RFC 形式存在于 GitHub Issues（#977），尚未完全开源。这一决策可能是出于商业竞争的考虑，但限制了社区的贡献和验证。[6]

生态集成分析

Mooncake 的生态集成策略是"深度嵌入，而非浅层对接"。它不是简单地提供一个传输 API，而是与各框架的核心机制深度耦合。[7]

vLLM 集成

vLLM 集成经历了三个阶段：[8][12][14]

  1. MooncakeConnector（PD 分离传输层）：实现 vLLM 的 KVConnectorBase_V1 接口，采用 ZMQ 侧信道协调 prefill/decode 两端的 KV 传输
  2. vLLM V1 Proxy Server（xPyD 分离代理）：实现 FastAPI 代理层，支持多个 prefill 实例和多个 decode 实例的 round-robin 调度
  3. Mooncake Store 作为分布式 KV 池：2026 年 5 月最新进展，从点对点传输升级为分布式 KV 池

竞争格局分析

Mooncake 的竞品主要来自三个方向，每个方向代表了不同的技术路线和生态策略。[13]

NVIDIA 生态

  • NCCL：集合通信模式不适合 P2P KV 传输，存在性能差和大故障域问题
    • NIXL：基于 UCX，支持 AMD GPU，但功能相对有限
  • 策略：通过 TensorRT-LLM 和 NIXL 构建封闭生态

学术项目

  • vLLM P2P 传输：针对特定场景的优化
  • SGLang RadixAttention：单点优化到系统化
  • 差异：从单点优化到系统化，而 Mooncake 从一开始就是系统化设计

云厂商方案

  • 阿里云 RBG：基于云基础设施的方案
  • AWS 推理服务：与云服务深度集成
  • 劣势：绑定特定云平台，Mooncake 的跨平台特性使其可以在任何环境中部署
本质差异

Mooncake 是"从 KVCache 出发"的架构设计，而竞品大多是"从计算出发"的优化。这种出发点的不同，决定了它们在 KVCache 管理上的深度和广度。

横纵交汇洞察（五问分析）

历史如何塑造了当下的竞争位置？

Mooncake 的诞生源于 Moonshot AI 在 Kimi 推理服务中遇到的真实痛点。2024 年 6 月，当大多数团队还在优化单机推理效率时，Moonshot AI 已经意识到 KVCache 的存储和传输将成为大规模推理的瓶颈。这一早期洞察使 Mooncake 在 KVCache-centric 架构上建立了先发优势。[2]

与学术驱动的项目不同，Mooncake 从一开始就是为生产环境设计的。它在 Moonshot AI 的数千节点集群上经过了实战检验，处理超过 1000 亿 token/天的生产负载。这种"从生产中来，到生产中去"的路径，使 Mooncake 在可靠性、性能和易用性上具有天然优势。

当前优势的历史根源可以追溯到 2024 年 7 月的技术报告发布。在这个时间点，Moonshot AI 做出了两个关键决策：(1) 将 KVCache 提升为一等公民；(2) 选择开放生态路线。这两个决策的组合效应是：Mooncake 既有了核心技术的深度，又有了生态集成的广度。

当前劣势的历史根源是 Moonshot AI 在开源策略上的保守。Conductor 调度器尚未完全开源，部分传输协议的性能数据未公开。这种策略在保护商业秘密的同时，也限制了社区的深度参与。

总结与展望

核心优势

  1. 架构创新性：KVCache-centric 分离式架构将 KVCache 从"计算的附属品"提升为"一等公民"
  2. 传输性能：Transfer Engine 在 8x400 Gbps RoCE 网络上实现 190 GB/s 聚合带宽，比 TCP 快 4.6x
  3. 生态广度：与 vLLM、SGLang、TensorRT-LLM、LMCache、LMDeploy 等主流框架深度集成
  4. 硬件覆盖：支持 9 家加速器厂商和 6 种网络 Fabric，是真正的跨平台方案
  5. 生产验证：在 Moonshot AI 的数千节点集群上经过实战检验，每日处理超过 1000 亿 token
  6. 社区活跃：GitHub 5358 stars，100+ 贡献者，PyTorch Ecosystem 成员

主要局限

  1. Conductor 未完全开源：全局调度器是核心组件，但目前以 RFC 形式存在
  2. 独立基准测试缺乏：性能数据主要来自官方论文和文档
  3. 超大规模集群数据有限：在万卡以上的集群中，调度性能和稳定性数据有限
  4. 国产硬件性能数据不完整：部分传输协议的具体性能数据未公开

技术演进方向

  • TENT V1.1（计划 2026 Q2 发布）：引入声明式切片喷射调度器，进一步提升传输性能[4]
  • 跨数据中心推理：PrfaaS 论文提出 Prefill-as-a-Service 概念，实现 54% 更高服务吞吐量，P90 TTFT 降低 64%[5]
  • Store V3 演进：更高效的存储后端和淘汰策略，ObjectDataType 分类为类型感知策略奠定基础
  • RL 训练支持：Mooncake RL 模块的出现，表明 Mooncake 正在向训练场景扩展
  • 专家并行支持：Mooncake EP 模块提供集合通信后端和专家并行内核
行业影响

Mooncake 的成功实践正在改变 LLM 推理的架构范式。从"以计算为中心"到"以 KVCache 为中心"的转变，不仅是技术层面的创新，更是思维方式的变革。随着 LLM 模型规模的持续增长和推理需求的爆发式增长，KVCache 管理将成为越来越关键的基础设施。
