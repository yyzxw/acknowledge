5.1 LMCache（多级 KV Cache 卸载）

KV Cache 扩展

定义

LMCache 是一个专为大规模 LLM 推理设计的 KV Cache 扩展层，定位于 vLLM 和 SGLang 等推理引擎的 KV Cache 管理增强组件。其核心使命是"让 LLM 对每个文本只执行一次 Prefill"——通过多级存储层次将 KV Cache 持久化，使任何服务引擎实例都能跨请求、跨会话甚至跨节点复用缓存，从而显著降低 Time-To-First-Token (TTFT) 并节省 GPU 计算周期。LMCache 由 LMCache 团队维护，与 vLLM Production Stack 同源，已被集成到上游 vLLM 的 KVConnector 架构中，提供即插即用体验。

多级存储层次

LMCache 实现了 GPU HBM → CPU DRAM → 本地 SSD/NVMe → 远程存储（S3/Redis） 的四级卸载层次：

层级配置项典型延迟容量用途
GPU HBM原生 vLLM KV Cache~1.5 TB/s 带宽有限（如 A100 80GB）当前活跃请求
CPU DRAMlocal_cpu: true, max_local_cpu_size~100 GB/s 带宽数 TB热数据缓存
本地 SSD/NVMelocal_disk: "file:///path"~7 GB/s 带宽数 TB~数十 TB温数据持久化
远程存储remote_url (S3/Redis/Valkey)网络延迟无限冷数据、跨节点共享
P2P 传输enable_p2p: trueRDMA 延迟不限实例间直接传输

关键配置参数（来自 lmcache/v1/config.py）：

  • chunk_size（默认 256）: KV Cache 分块大小，影响存储粒度和索引效率
  • local_cpu（默认 True）: 是否启用 CPU offloading
  • max_local_cpu_size（默认 5.0 GB）: 本地 CPU 缓存最大容量
  • local_disk: 本地磁盘路径，用于磁盘级 offloading
  • remote_url: 远程存储 URL，支持 S3、Redis 等后端
  • enable_pd / pd_role: Disaggregated Prefill 角色配置

Disaggregated Prefill

Disaggregated Prefill（又称 PD 分离）是 LMCache 的高级特性，将计算密集的 Prefill 阶段和内存带宽密集的 Decode 阶段部署到不同的 GPU 集合上。LMCache 支持基于 NIXL（NVIDIA Dynamo 的通信抽象）的跨实例 KV Cache 传输，NIXL 支持 NVLink、RDMA 网卡和 GPU Direct Storage。

PD 分离中的 KV 传输路径：

vLLM Prefill Node → LMCache Server → vLLM Decode Node

配置示例：

# Prefiller 端
local_cpu: False
enable_pd: True
transfer_channel: "nixl"
pd_role: "sender"
pd_proxy_host: "localhost"
pd_proxy_port: 7500
nixl_backends: [UCX]

# Decoder 端
local_cpu: False
enable_pd: True
transfer_channel: "nixl"
pd_role: "receiver"
pd_peer_host: "localhost"
pd_peer_init_port: 7300
pd_buffer_size: 2147483648  # 2GB
nixl_backends: [UCX]

与传统 PD 分离方案相比，LMCache 避免了细粒度 KV Cache 传输导致的带宽利用率不足问题，通过批量化数据移动和计算与 I/O 流水线技术，实现了更高的传输效率。

P2P Sharing（跨节点 KV Cache 共享）

P2P 共享允许 vLLM 实例直接交换 KV Cache，无需经过中央存储。各实例形成一个分布式缓存网络，请求可以被路由到已缓存相关前缀的实例。P2P 配置包括：

  • enable_p2p: 启用 P2P 共享
  • p2p_host: P2P 主机地址
  • p2p_init_ports / p2p_lookup_ports: 端口配置

当 Decode 实例收到请求后，首先通过 P2P 网络查询远程 Prefill 实例上是否存在对应的 KV Cache，若命中则直接拉取，跳过重复计算。

与 vLLM 的集成方式

LMCache 与 vLLM V1 的 KVConnector 架构深度集成，实现了 KVConnectorBase_V1 的子类，扮演两种角色：

关键接口方法：

  • get_num_new_matched_tokens(): 获取远程 KV Cache 中匹配的新 token 数
  • start_load_kv(): 异步加载 KV Cache
  • save_kv_layer(): 逐层保存 KV Cache
  • request_finished(): 请求完成时处理 KV Cache 释放

RequestTracker 数据结构追踪每个请求的缓存状态：

性能数据

根据 LMCache 官方论文和测试数据：

  • 3-10x 延迟节省：在多轮 QA 和 RAG 场景中，LMCache 可实现 3-10 倍的延迟降低和 GPU 计算周期减少
  • SGLang 集成：在 Qwen3-32B (TP=2) 上，LMCache 的 CPU offloading 相比无 offloading 的 SGLang 获得更高吞吐和更低 TTFT；与 SGLang 原生 CPU offloading 性能相当，但支持分布式存储后端

与其他概念的关系

LMCache 与 vLLM 的 Prefix Caching 互补：vLLM 的本地 prefix caching 处理同实例内的请求间共享，LMCache 扩展了跨实例和跨存储层次的共享能力。在 PD 分离架构中，LMCache 作为 KV Cache 传输层，连接 Prefill 池和 Decode 池。在 Production Stack 中，LMCache 是默认集成的 KV Cache 扩展组件。

5.2 SGLang

推理框架

定义

SGLang（Structured Generation Language）是由 LMSYS 团队开发的高性能 LLM 推理和服务框架，与 vLLM 处于同一生态位，但采用了不同的架构路线。SGLang 不仅是一个推理引擎，还包含一个 Python 嵌入式 DSL，用于表达复杂的 LLM 程序工作流，如多轮对话、工具调用、树状思考等。其核心定位是面向生产规模部署的高性能推理系统，特别擅长处理具有重复提示模式的工作负载（聊天机器人、RAG、多轮 Agent），支持 400,000+ GPU 的超大规模生产部署（如 DeepSeek）。

RadixAttention：Radix Tree 前缀缓存

RadixAttention 是 SGLang 最具标志性的创新，是一种在运行时自动且系统化地复用 KV Cache 的技术。与 vLLM 在处理完生成请求后丢弃 KV Cache 不同，SGLang 将提示词和生成结果的 KV Cache 保留在一个 Radix Tree（基数树/压缩前缀树） 数据结构中，实现高效的前缀搜索、复用、插入和驱逐。

Radix Tree 数据结构（来自 sglang/srt/mem_cache/radix_cache.py）：

class TreeNode:
    def __init__(self, id=None, priority=0):
        self.children = defaultdict(TreeNode)
        self.parent: TreeNode = None
        self.key: RadixKey = None
        self.value: Optional[torch.Tensor] = None          # GPU 上的 KV Cache
        self.lock_ref = 0
        self.last_access_time = time.monotonic()
        self.hit_count = 0
        self.host_value: Optional[torch.Tensor] = None     # CPU 备份
        self.priority = priority

class RadixKey:
    def __init__(self, token_ids: List[int], extra_key: Optional[str] = None):
        self.token_ids = token_ids
        self.extra_key = extra_key  # 区分不同 LoRA 或缓存盐值

前缀匹配算法按 page_size 粒度比较 token 序列，与 GPU 上的页式 KV Cache 管理对齐：

def _key_match_paged(key0, key1, page_size):
    _check_extra_key(key0, key1)
    min_len = min(len(key0), len(key1))
    i = 0
    while i < min_len:
        if key0.token_ids[i:i+page_size] != key1.token_ids[i:i+page_size]:
            break
        i += page_size
    return i

与 vLLM Block Hash 前缀缓存的对比

特性SGLang RadixAttentionvLLM PagedAttention + Prefix Caching
数据结构Radix Tree（压缩前缀树）Block Table + 哈希表
匹配粒度Token 序列（支持页粒度）固定 Block（默认 16 tokens）
复用范围任意前缀（包括生成结果）主要是提示词前缀
驱逐策略LRU + 优先级感知LRU（V1）
调度协同缓存感知调度（优先命中请求）标准调度 + Prefix Caching 辅助

适用场景多轮对话、Agent、复杂工作流单轮请求、批处理

核心区别：

  1. 树 vs 表：Radix Tree 天然支持变长前缀共享，而 vLLM 的 block hash 是固定块级别的匹配。当对话历史在不同请求间有细微差异（如时间戳、用户名）时，Radix Tree 可以在不同分支上共享公共前缀，而 vLLM 的 block hash 可能完全失效。
  2. 生成结果缓存：SGLang 将生成结果也缓存到 Radix Tree 中，支持多轮对话的完整历史复用；vLLM 的 prefix caching 主要针对输入提示词。
  3. 调度协同：SGLang 的调度器会优先调度能命中缓存的请求，vLLM 的调度器在这方面的集成较浅。

性能数据：关闭 RadixAttention 会使吞吐下降 70-90%；SGLang 在端到端 Agentic、推理和长上下文任务上比基线 vLLM 和 LMQL 高 4-6 倍吞吐。在 80% 共享前缀的工作负载下，SGLang 的 TTFT 比 vLLM 快 2-6 倍。

Structured Outputs：压缩 FSM 加速约束解码

Structured Outputs 是 SGLang 的关键特性，用于约束 LLM 生成符合特定格式（JSON Schema、正则表达式）的输出。不同于传统 rejection sampling（生成后检查，不符合则重试），SGLang 将 JSON Schema 或正则表达式编译为压缩有限状态机（FSM），在采样阶段直接引导生成过程。

FSM 由状态集合、输入字母表、转移函数、初始状态和接受状态组成。在约束解码中，FSM 的状态表示当前解析位置，转移表示允许的下一个 token。SGLang 的压缩 FSM 优化实现了 3 倍更快的 JSON 解码。

class Scheduler:
    def __init__(self, ...):
        # 初始化时即创建 GrammarManager
        self.structured_output_manager = GrammarManager(...)

应用场景包括：工具调用（强制 LLM 输出符合预定义的工具参数格式）、API 响应格式化（确保可解析的 JSON）、数据抽取（从文本中抽取结构化信息）、代码生成（约束语法规则）。

Zero-overhead CPU Scheduler

LLM 推理不仅消耗 GPU 资源，CPU 也需要承担大量工作：批调度、内存分配、前缀匹配等。未优化的推理引擎中 CPU 开销可能高达一半的总推理时间。SGLang 的 Zero-overhead CPU Scheduler 将 CPU 调度与 GPU 计算重叠——调度器提前一个批次运行，准备下一个批次所需的所有元数据，使 GPU 始终处于忙碌状态，昂贵的 Radix Tree 操作等开销被完全隐藏。

这一思想在 NanoFlow 论文中已有提出，SGLang v0.4 将其推至极致实现。调度器的复杂组成包括：schedule_policy.py（调度策略）、schedule_batch.py（批次管理）、scheduler_dp_attn_mixin.py（Data Parallel Attention 混合）等模块。

5.3 Gateway / 推理网关

路由

定义

Gateway API Inference Extension 是由 Kubernetes SIG（Special Interest Group）推出的推理网关扩展项目，隶属于 kubernetes-sigs 组织。它将 Kubernetes Gateway API 从通用的 L7 路由基础设施扩展为推理感知（Inference-Aware）的智能网关，使 LLM 推理服务具备"模型即服务"（Model-as-a-Service）的能力。项目引入了两个新的 Custom Resource Definitions（CRDs）：InferencePool（推理工作负载的后端集合）和 InferenceModel（客户端可见模型名到后端 LoRA 适配器/目标模型的映射）。

Prefix Cache 感知路由

传统负载均衡器（如轮询）不考虑各实例的 KV Cache 状态，可能将请求路由到没有缓存前辍的实例，导致需要完整 prefill。Prefix Cache 感知路由的核心原理是：将请求路由到已经持有相关前缀缓存的实例，从而避免重复的 prefill 计算，降低 TTFT。

Endpoint Picker (EPP) 是 Inference Extension 的核心调度组件，通过 Envoy 的 ext_proc 过滤器接收请求信息，结合从 Model Serving 平台获取的实时指标做出最优端点选择：

  1. Gateway 选择正确的 InferencePool
  2. Gateway 将请求信息转发给 Endpoint Selection Extension
  3. Inference Gateway 从 Model Serving 获取实时指标（Prefix Cache 状态、LoRA 可用性等）
  4. EPP 基于指标和请求特征选择最优端点
  5. Envoy 将请求路由到选定的端点

LoRA Adapter 路由

在生产环境中，通常在同一个基础模型上加载多个 LoRA 适配器以服务不同任务。Gateway 提供三层面的 LoRA 路由支持：

  • 路由到已加载的实例：优先将请求发到已持有该 LoRA 的 GPU
  • 路由到可加载的实例：若无实例已加载，发到有能力加载的实例
  • 动态加载决策：基于适配器使用频率缓存热度做换入换出决策

配置示例：

apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferenceModel
metadata:
  name: tweet-summary
spec:
  modelName: tweet-summary
  criticality: Critical
  targetModels:
  - name: tweet-summary-0
    weight: 90
  - name: tweet-summary-1
    weight: 10

通过 weight 字段可实现蓝绿发布或金丝雀发布。大规模 LoRA 服务的核心挑战包括：数万个适配器注册、适配器使用极不均衡（少数高频大量低频）、不同适配器需要不同的 SLO 层级。

Criticality 分级

Criticality 分级允许为不同请求设置不同的服务优先级：

  • Critical（关键）: 延迟敏感任务（如在线聊天），优先负载均衡
  • Sheddable（可丢弃）: 延迟容忍任务（如摘要生成），负载过高时可丢弃

EPP 的过滤器链按以下顺序评估：

对于关键请求：

  1. Critical Request Check: 判断是否关键
  2. Low Queuing Filter: 筛选队列 < 50 的端点
  3. LoRA Affinity Check: 筛选已加载所需 LoRA 的端点
  4. Least Queuing Filter: 选择队列最短的端点
  5. Least KV Cache Filter: 选择 KV Cache 利用率最低的端点

对于非关键请求（Sheddable）：

  1. Has Capacity Filter: 筛选 KV Cache < 80% 且队列 < 5 的端点
  2. 若无可满足条件的端点，直接丢弃请求

示例场景：

关键请求 + LoRA-X：
  Pod A: Queue=6, KV=85%, LoRA-X=loaded    → 通过 LoRA 亲和性 → 最终选中
  Pod B: Queue=4, KV=75%, LoRA-X=not loaded → 不通过 LoRA 亲和性
  Pod C: Queue=7, KV=60%, LoRA-X=not loaded → 不通过 LoRA 亲和性

基于 GPU 指标的智能路由

除了 Prefix Cache 和 LoRA 状态，Gateway 还考虑以下 GPU 指标：

  • KV Cache 利用率: 各实例的 KV Cache 使用比例
  • 队列长度: 等待处理的请求数
  • GPU 利用率: 计算资源使用率
  • 请求成本: 预估的推理成本

与 Envoy 的集成

Gateway 利用 Envoy 的 External Processing (ext_proc) 过滤器实现扩展：

Client → Envoy Proxy → ext_proc → EPP (Endpoint Picker)
                               →
                        InferencePool/InferenceModel CRDs

已知集成实现：kgateway（原 Envoy Gateway，原生支持）、Istio（通过设置 SUPPORT_GATEWAY_API_INFERENCE_EXTENSION=true 启用）、GKE Inference Gateway（Google Cloud 托管实现）。

5.4 Production Stack（生产部署栈）

部署

定义

vLLM Production Stack（亦称 vllm-stack 或 llmstack）是 vLLM 的生产级部署参考实现，由 LMCache 团队维护。它是一个 Kubernetes 原生的推理栈，在 vLLM 之上增加了四个关键能力：KV Cache 共享与存储（通过 LMCache）、Prefix-aware 路由、可观测性（TTFT/TBT/吞吐监控）、自动扩缩容。

Helm / Kubernetes 部署

通过 Helm Chart 一键部署到 Kubernetes：

# 最小化部署

HPA / VPA 自动扩缩容

Production Stack 使用 KEDA（Kubernetes Event-driven Autoscaling）实现基于自定义指标的自动扩缩容：

keda:
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus:9090
      metricName: vllm_num_requests_waiting
      query: vllm:num_requests_waiting
      threshold: "5"
  advanced:
    restoreToOriginalReplicaCount: false

servingEngineSpec:
  modelSpec:
  - name: "llama3"
    replicaCount: 1
    keda:
      minReplicaCount: 1
      maxReplicaCount: 3
      triggers:
      - type: prometheus
        metadata:
          query: vllm:num_requests_waiting
          threshold: "5"

配置要点：基于 vllm:num_requests_waiting 指标触发扩缩容，副本范围 1-3，扩容阈值队列长度 > 5，检查周期 15 秒，缩容冷却 360 秒（避免抖动）。

5.5 LoRA / QLoRA

参数高效微调

LoRA 数学原理

LoRA（Low-Rank Adaptation）是一种参数高效微调（PEFT）方法，基于关键假设：模型权重在微调过程中的更新具有低内在秩（low intrinsic rank）。标准微调更新预训练权重矩阵 W₀ ∈ ℝ^(d×k) 为 W = W₀ + ΔW，其中 ΔW 包含 d×k 个参数。

LoRA 将 ΔW 分解为两个低秩矩阵的乘积：

W = W₀ + BA

其中 B ∈ ℝ^(d×r)，A ∈ ℝ^(r×k)，秩 r ≪ min(d, k)。总参数量从 d×k 减少到 r×(d+k)。

带缩放因子的前向传播：

h = W₀x + (α/r) · BAx

其中 α 是缩放因子。训练开始时 A 随机高斯初始化，B 初始化为零，确保模型输出与预训练模型一致。

计算效率对比（以 1000×1000 矩阵为例）：

  • 全量微调：ΔW 有 1,000,000 参数
  • LoRA (r=2)：A 是 1000×2，B 是 2×1000，共 4,000 参数，参数量减少 250 倍

QLoRA：4-bit NormalFloat + Double Quantization + Paged Optimizers

QLoRA（Quantized LoRA）通过三种技术将 LoRA 的内存需求进一步降低：

1. 4-bit NormalFloat (NF4)： NF4 基于权重通常服从正态分布的观察，使用信息论最优的非均匀量化点。量化级别通过拟合标准正态分布 N(0,1) 的分位数确定，在 4 位（16 个级别）约束下最小化量化误差。

2. Double Quantization（双重量化）： 第一次量化将权重从 fp16/bf16 量化为 4-bit，但量化本身需要存储 scale 参数（fp32）。Double Quantization 将这些 scale 参数再次量化（例如到 8-bit），进一步减少内存开销。

3. Paged Optimizers（分页优化器）： 使用 NVIDIA 统一内存管理优化器状态。当 GPU 显存不足时，优化器状态页自动转移到 CPU 内存，需要时再换入，避免训练过程中的 OOM 错误。

内存节省对比（7B 参数模型）：

方法权重优化器状态总计
全量微调 fp16~14GB~42GB~56GB
LoRA fp16~14GB很小~14GB+
QLoRA NF4~4GB分页管理~4GB+

QLoRA 使得在消费级 GPU（如 24GB RTX 4090）上微调 70B 参数模型成为可能。

LoRAModelManager（vllm/lora/model_manager.py）实现适配器的全生命周期管理：

class LoRAModelManager:
    def __init__(self, model, max_num_seqs, max_num_batched_tokens,
                 vocab_size, lora_config, device, vllm_config):
        self._registered_adapters: dict[int, LoRAModel] = {}
        self._active_adapters: dict[int, None] = {}
        self.lora_index_to_id: list[int | None] = [None] * self.lora_slots
        self.punica_wrapper_mapping: dict[str, PunicaWrapperBase] = {}

核心机制：

  • 注册适配器：_registered_adapters 存储所有已加载的 LoRA
  • 活跃适配器：_active_adapters 跟踪当前批次中使用的 LoRA（支持同一批次中混用不同 LoRA）
  • LRU 缓存：AdapterLRUCache 管理 GPU 内存中的 LoRA，超出容量时驱逐到 CPU
  • PunicaWrapper：高效的批量 LoRA 计算内核封装，通过批量化低秩矩阵乘法实现多适配器零额外开销

S-LoRA 架构

S-LoRA（Scalable Low-Rank Adaptation）是 vLLM LoRA 支持的底层架构，实现了高效的服务数千个 LoRA 适配器的系统。其核心技术贡献包括：

  1. Unified Paging：统一管理 LoRA 权重页和 KV Cache 页，实现统一内存池
  2. Dynamic Adapter Batching：在同一批次中混合不同 LoRA 适配器的请求，通过 Punica 内核实现高效执行
  3. Punica Kernel：专门为批量 LoRA 计算设计的 CUDA kernel，接收不同适配器的低秩矩阵 A 和 B，一次性完成批量化计算

LoRA 前缀缓存共享机制

在 vLLM 中，LoRA 请求的前缀缓存通过 extra_key 机制区分。hash_block_tokens 函数在计算 block hash 时结合 LoRA 名称，确保不同 LoRA 适配器下的同一 token 序列被视为不同的缓存实体：

def hash_block_tokens(token_ids, extra_keys=None):
    # extra_keys 中包含 lora_name
    # 使得不同 LoRA 下同一前缀产生不同的哈希值
    return hash(tuple(token_ids) + tuple(extra_keys or []))

这意味着同一基础模型+同一前缀在不同 LoRA 适配器下会分别缓存。SGLang 的 RadixAttention 采用类似的机制，其 RadixKey.extra_key 也用于区分 LoRA 适配器。

与 Gateway 的协同

Gateway API Inference Extension 原生支持 LoRA Adapter 路由，通过 InferenceModel CRD 定义客户端可见模型名到 LoRA 适配器的映射。在大规模 LoRA 服务（数万适配器）场景下，架构方案为：

  1. 适配器分层：热适配器常驻 GPU，温适配器在 CPU，冷适配器按需加载
  2. 请求-适配器协同迁移：动态迁移请求和适配器以优化延迟
  3. 动态跨适配器批处理：vLLM 原生支持同一批次中混合使用不同 LoRA 的请求
